## Round 1 — Initial Review

### R001-F001 — Implementer status-write duty contradicts ownership boundary

**Round:** 1
**Severity:** Critical
**Status:** Open
**Location:** `SPEC.md` §12 (Implementer), §17.2 (Handoff between agents); `SKILL.md` Implement permissions and Handoff

SPEC §12 requires the implementer to not modify reviewer-owned review artifacts ("MUST NOT modify reviewer-owned review artifacts"), while §17.2 instructs that "an implementing agent SHOULD update the finding status to In Progress or Resolved before proceeding." `SKILL.md` repeats both sides: the Implement operation forbids writing reviewer-owned review records, and the Handoff section instructs the implementing agent to update the finding status. A conformant agent cannot satisfy both rules at once.

**Recommendation**

Remove the implementer's duty to write the review record. The implementer reports progress and completion through their own feedback items (§8.5) or external channels; the review owner records the resulting status change. Reword §17.2's handoff rule so the review record is updated by the review owner before another agent operates.

**Acceptance**

- [ ] SPEC §17.2 no longer instructs the implementer to write the review record.
- [ ] SPEC §17.2 assigns status recording to the review owner and names a reporting channel for implementers.
- [ ] `SKILL.md` Implement and Handoff sections are consistent with the revised rule.

### R001-F002 — Example records contradict the Section 10 state model

**Round:** 1
**Severity:** High
**Status:** Open
**Location:** `examples/code-review.md` (R042-F002), `examples/document-review.md` (R017-F001), `examples/multi-round-review.md` (header and Review Outcome)

Three example records are internally inconsistent with the state model in SPEC §10:

- `R042-F002` has `**Status:** Open` while recording `**Decision:** Accepted Alternative`; per §10 an accepted decision is not an Open state.
- `R017-F001` records `**Decision:** Discussing`, conflating a process state (§10) with a decision outcome (§11).
- `R055` header states `**Status:** Open` while its Review Outcome section states `**Status:** Closed`; the record contradicts itself and is the only closure example in the repository.

**Recommendation**

Correct the three records: set R042-F002 status to `Accepted Alternative`; drop the `Decision` line for R017-F001 (the Status field carries the state, e.g. `Discussing`); set the R055 header status to `Closed`.

**Acceptance**

- [ ] No example record pairs an Open status with a recorded decision outcome.
- [ ] No example records a process state as a Decision value.
- [ ] Each example record's status matches its outcome representation.

### R001-F003 — Review status vocabulary and closure representation undefined

**Round:** 1
**Severity:** High
**Status:** Open
**Location:** `SPEC.md` §6, §7, §13.9; `schemas/review.schema.json` (status enum); `examples/` (Review Outcome sections)

§6 requires each review record to contain a "review status" but no values are defined anywhere in the specification. `schemas/review.schema.json` hardcodes the enum `Open | Closed`, which is stricter than the spec. §13.9 permits the reviewer to close a review but does not specify how closure is represented in the record. The examples use a "Review Outcome" section that appears nowhere in the specification, so conformant records cannot be derived from the normative text alone.

**Recommendation**

Define the review status vocabulary in §6 as `Open` and `Closed`, matching the schema enum. Specify the closure representation in §13.9: on closure the reviewer sets the record status to `Closed` with a date and rationale (consistent with §17's status-change rationale requirement), and MAY include an outcome summary section (normatizing the examples' "Review Outcome" section as optional).

**Acceptance**

- [ ] §6 defines the allowed review status values, consistent with `schemas/review.schema.json`.
- [ ] §13.9 specifies how closure is represented in the record.
- [ ] Example closure representation matches the normative rule.

### R001-F004 — No Markdown-to-schema projection mapping

**Round:** 1
**Severity:** Medium
**Status:** Open
**Location:** `SPEC.md` §18; `schemas/review.schema.json`, `schemas/feedback.schema.json`; `AGENTS.md` (Building and validating)

The schemas are described as optional machine-readable projections of the Markdown records, but nothing defines how the projection is derived: how `Current Round` maps to `current_round`, how `### R###-F###` headings map to finding `id` and `title`, how checkbox lists map to the `acceptance` array, or how feedback item headings map to item fields. Consequently `AGENTS.md`'s instruction to "validate examples against `schemas/review.schema.json`" is not actionable as written.

**Recommendation**

Add a projection mapping table to §18 (or an appendix) defining the derivation of both JSON projections from the Markdown records, including feedback threads and item headings.

**Acceptance**

- [ ] The spec defines the Markdown field to schema property mapping for reviews and feedback threads.
- [ ] `AGENTS.md`'s validation guidance references the defined mapping.

### R001-F005 — Feedback item fields under-specified; schema role enum conflicts

**Round:** 1
**Severity:** Medium
**Status:** Open
**Location:** `SPEC.md` §8.5; `schemas/feedback.schema.json` (author_role); `examples/feedback-loop.md`

Three related gaps in the feedback format:

- The examples label items with kinds (Clarification, Response, Confirmation) that are not part of §8.5's recommended item fields, so the convention is undefined.
- Items record only an author role, not an author identity, which weakens ownership enforcement when multiple reviewers or implementers participate.
- §8.5 frames feedback as an exchange "between reviewers and implementers", while `feedback.schema.json` closes `author_role` to `Reviewer | Implementer | Verifier`; the Verifier participant is never acknowledged in §8.5's text, and no extension mechanism is defined for other roles.

**Recommendation**

In §8.5: normatize the `## FB### — Kind` heading pattern with recommended kinds (Clarification, Response, Confirmation, Report); allow an optional author identity alongside the role; acknowledge the Verifier as a valid feedback participant; state that repositories MAY extend the role vocabulary. In `schemas/feedback.schema.json`: change `author_role` from a closed enum to a string with the recommended values documented in the description, and add an optional `author` property.

**Acceptance**

- [ ] §8.5 defines the item kind convention and recommended values.
- [ ] §8.5 allows an optional author identity field.
- [ ] §8.5 and `feedback.schema.json` agree on valid participant roles and extension.

### R001-F006 — No legal status-transition rules

**Round:** 1
**Severity:** Medium
**Status:** Open
**Location:** `SPEC.md` §10, §13.11

§10 defines the state vocabulary with per-state definitions but no transition rules: which moves are legal, whether a Verified finding may become Stale, or whether a Stale finding may reopen. §13.11 covers decision revocation only. There is also no linkage between feedback activity and the Discussing state, so agents have no guidance on when Discussing applies.

**Recommendation**

Add a compact transition table to §10, for example: Open and Discussing may move to any decision outcome; Accepted and Accepted Alternative progress through In Progress, Resolved, and Verified; terminal outcomes are final within the current review, with reopening governed by §13.11 and Stale semantics stated explicitly (including whether Stale may reopen). Note that opening or participating in a feedback thread MAY be reflected by setting the finding status to Discussing.

**Acceptance**

- [ ] §10 defines legal transitions or explicitly delegates transition control to repositories.
- [ ] Stale reopening semantics are specified.
- [ ] The relationship between feedback activity and Discussing is stated.

### R001-F008 — Verification evidence reproducibility and scope anchoring unspecified

**Round:** 1
**Severity:** Low
**Status:** Open
**Location:** `SPEC.md` §4 (Scope), §8 (finding fields); `SKILL.md` Verify procedure

The spec requires "verification evidence when verified" but sets no quality bar. Evidence such as "Payment client timeout tests pass" (in `examples/code-review.md`) is not reproducible. Likewise, Scope is defined as artifact paths with no recommendation to anchor a review to a specific changeset, which weakens reproducibility of the review itself.

**Recommendation**

Add SHOULD-level guidance: verification evidence SHOULD be reproducible (record commands, test names, or commit references); review scope SHOULD record a commit or pull-request reference when the review covers a changeset.

**Acceptance**

- [ ] The spec includes reproducible-evidence guidance.
- [ ] The spec includes changeset-anchoring guidance for scope.

### R001-F011 — Schema strictness is inconsistent

**Round:** 1
**Severity:** Low
**Status:** Open
**Location:** `schemas/review.schema.json`, `schemas/feedback.schema.json`

`feedback.schema.json` sets `additionalProperties: false` on feedback items but not on the thread object itself, while `review.schema.json` never sets `additionalProperties: false` at the record or finding level. `decision` is unconstrained free text in the review schema while sibling fields use enums. Neither schema declares an `$id`.

**Recommendation**

Apply a consistent `additionalProperties` policy across both schemas and both levels; consider an enum for `decision` aligned with §10; add `$id` declarations.

**Acceptance**

- [ ] Both schemas apply a consistent additionalProperties policy.
- [ ] Schema strictness choices are documented or justified.
