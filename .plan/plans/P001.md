# P001 — Redesign RaC Core Domain and Lifecycle Model

**Status:** Active
**Scope:** `review-as-code/`
**Planner:** planner-agent
**Created:** 2026-09-14
**PaC version:** v0.3.2
**Current iteration:** 1

## Objective

Redesign the Review as Code (RaC) core domain and finding lifecycle to provide a simpler, clearer and more agent-friendly model based on two roles, independent lifecycle dimensions, append-only logs and derived current state.

The resulting model MUST clearly distinguish:

* who creates and implements changes to reviewed artifacts;
* who reviews and verifies those changes;
* what has been decided about a finding;
* what has been implemented;
* what has been verified; and
* the current derived state of the finding.

The redesign MUST remain lightweight, Git-native, human-readable and avoid introducing a complex workflow state machine.

## Scope

### Included

* RaC role model.
* Finding lifecycle model.
* Decision Log.
* Implementation Log.
* Verification Log.
* Derived `State`.
* Finding closure semantics.
* Related normative terminology and workflow documentation.
* Corresponding examples and schemas required to represent the new model.

### Excluded

* Finding classification, severity and confidence improvements.
* Structured location improvements.
* Review-level outcome and review type.
* Reference validator implementation.
* CI integration.
* Agent CLI/query tooling.
* Other Workstream 2–5 improvements.

## Constraints

* Markdown remains the canonical representation.
* Git/repository filesystem remains the system of record.
* Each finding remains independently writable.
* Lifecycle logs are append-only.
* Historical log entries MUST NOT be rewritten.
* `State` is derived/materialised and MUST NOT become the authoritative history.
* No central mutable registry or database.
* No complex transition matrix or workflow engine.
* Discussion remains external to the RaC record.
* Lifecycle logs contain decision-relevant information, not discussion transcripts.
* Existing stable review and finding IDs MUST be preserved when records are migrated.

## Tasks

### P001-T001 — Redesign RaC roles

**Status:** Planned
**Owner:** Implementer

Replace the current `Reviewer`, `Artifact Owner` and `Verifier` role model with two core roles: `Author` and `Reviewer`.

#### Acceptance

- [ ] AC-P001-T001-01 — The core RaC role model defines only `Author` and `Reviewer`.
- [ ] AC-P001-T001-02 — `Author` is the creator of the artifacts under review and implements accepted findings.
- [ ] AC-P001-T001-03 — `Reviewer` reviews artifacts, creates findings, participates in finding decisions and verifies remediation.
- [ ] AC-P001-T001-04 — `Artifact Owner` and `Verifier` are removed as core RaC roles.
- [ ] AC-P001-T001-05 — Specification, agent instructions, examples and schemas use the new role model consistently.
- [ ] AC-P001-T001-06 — The model allows a policy to require independent verification by a different Reviewer without introducing a separate `Verifier` role.

### P001-T002 — Define independent finding lifecycle dimensions

**Status:** Planned
**Owner:** Implementer
**Depends on:** P001-T001

Define `Decision`, `Implementation` and `Verification` as independent lifecycle dimensions of a finding.

#### Acceptance

- [ ] AC-P001-T002-01 — Decision, Implementation and Verification are explicitly defined as independent dimensions.
- [ ] AC-P001-T002-02 — An accepted finding can remain unimplemented.
- [ ] AC-P001-T002-03 — An implemented finding can remain unverified.
- [ ] AC-P001-T002-04 — Failed verification does not erase or invalidate implementation history.
- [ ] AC-P001-T002-05 — The model does not require a global state-transition matrix.
- [ ] AC-P001-T002-06 — The rules for deriving the current finding state and closure condition are explicitly defined.

### P001-T003 — Introduce dedicated append-only lifecycle logs

**Status:** Planned
**Owner:** Implementer
**Depends on:** P001-T002

Introduce dedicated logs for each lifecycle dimension:

* `Decision Log`
* `Implementation Log`
* `Verification Log`

#### Acceptance

- [ ] AC-P001-T003-01 — Each lifecycle dimension has its own append-only log.
- [ ] AC-P001-T003-02 — Each log entry has a stable identifier, actor and date.
- [ ] AC-P001-T003-03 — Both `Author` and `Reviewer` can contribute to the Decision Log.
- [ ] AC-P001-T003-04 — Implementation Log entries are authored by the `Author`.
- [ ] AC-P001-T003-05 — Verification Log entries are authored by the `Reviewer`.
- [ ] AC-P001-T003-06 — Historical log entries cannot be rewritten as part of normal lifecycle progression.
- [ ] AC-P001-T003-07 — Logs contain decision-relevant information rather than discussion transcripts.
- [ ] AC-P001-T003-08 — Implementation evidence can reference Git-native artifacts such as commits, pull requests or changed files.

### P001-T004 — Replace Snapshot with derived State

**Status:** Planned
**Owner:** Implementer
**Depends on:** P001-T003

Replace the previously considered `Snapshot` concept with `State` as the materialised representation of the current finding condition.

#### Acceptance

- [ ] AC-P001-T004-01 — The normative terminology uses `State`, not `Snapshot`.
- [ ] AC-P001-T004-02 — `State` represents the current Decision, Implementation and Verification values.
- [ ] AC-P001-T004-03 — `State` is derived from the finding record and lifecycle logs.
- [ ] AC-P001-T004-04 — Lifecycle logs remain the authoritative historical record.
- [ ] AC-P001-T004-05 — Agents can determine the current finding condition without processing the complete historical context when a valid `State` is available.
- [ ] AC-P001-T004-06 — `State` does not introduce unnecessary duplication of historical information.
- [ ] AC-P001-T004-07 — `State` does not require a central registry or database.

### P001-T005 — Define finding closure semantics

**Status:** Planned
**Owner:** Implementer
**Depends on:** P001-T004

Define when a finding can be considered complete based on its independent lifecycle dimensions.

#### Acceptance

- [ ] AC-P001-T005-01 — Closure semantics are explicitly defined in the specification.
- [ ] AC-P001-T005-02 — An `accepted` finding with pending implementation is not closed.
- [ ] AC-P001-T005-03 — An implemented finding with pending verification is not closed when verification is required.
- [ ] AC-P001-T005-04 — Failed verification prevents closure when verification is required.
- [ ] AC-P001-T005-05 — Closure semantics are defined for `rejected`, `accepted_risk`, `deferred` and `not_applicable`.
- [ ] AC-P001-T005-06 — `not_required` verification is supported where applicable.
- [ ] AC-P001-T005-07 — The current state and closure condition can be derived deterministically.
- [ ] AC-P001-T005-08 — Closure semantics do not require a complex workflow state machine.

### P001-T006 — Update canonical finding structure and examples

**Owner:** Implementer

The target conceptual structure is:

```text
Finding
├── State
├── Observation
├── Recommendation
├── Decision Log
├── Implementation Log
└── Verification Log
```

#### Acceptance

- [ ] AC-P001-T006-01 — The canonical finding structure represents `State`.

- [ ] AC-P001-T006-03 — The canonical finding structure contains an Implementation Log.
- [ ] AC-P001-T006-04 — The canonical finding structure contains a Verification Log.
- [ ] AC-P001-T006-05 — Examples demonstrate an accepted, implemented and verified finding.
- [ ] AC-P001-T006-06 — Examples demonstrate an accepted but not yet implemented finding.
- [ ] AC-P001-T006-07 — Examples demonstrate an implemented but not yet verified finding.
- [ ] AC-P001-T006-08 — Examples demonstrate failed verification without losing implementation history.
- [ ] AC-P001-T006-09 — Existing examples are migrated without changing stable finding identifiers.
